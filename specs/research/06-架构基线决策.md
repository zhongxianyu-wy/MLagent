## 一、决策摘要

### 1.1 最终架构基线

**采用"核心三角 + 可选工具 + 设计参考"三层架构。**

| 层级 | 决策 | 理由 |
|------|------|------|
| **核心三角（Layer 2+3）** | AIDE fork + mem0 pip install + MLflow pip install | 唯一经 MLE-Bench 验证的探索引擎 + 56K stars 语义记忆 + 行业标准追踪，三者零依赖冲突，集成评估推荐分 9/10 |
| **可选工具（Layer 4）** | OpenFE pip install + Featuretools pip install | 算法驱动特征工程工具，定位"Agent 可调用工具箱"，非核心路径，可按需移除 |
| **设计参考** | CAAFE + Jupyter AI + Notebook Intelligence | 只学习设计模式，不复用代码。规避 GPL-3.0 风险、openai 版本冲突、安全漏洞 |
| **排除** | AutoML-Agent（CC BY-NC）/ 全自建 | 法律禁止 / 工程不经济（11-16 周 vs 7-8 周） |

### 1.2 与 04-决策汇总的差异

| 项目 | 04-决策汇总 | 06-架构基线决策 | 变更原因 |
|------|------------|----------------|---------|
| CAAFE | 拆出核心逻辑参考 | **降级为纯设计参考** | openai==0.28 与 AIDE/mem0 的 openai>=1.69 硬冲突（集成评估 4/10） |
| Notebook Intelligence | 直接复用代码 | **降级为纯设计参考** | GPL-3.0 convey 风险被低估 + PR #290/#323 路径遍历漏洞 |
| OpenFE | pip install | **保留但增加内存限制** | Issue #62/#53 OOM 对 NGS 高维数据致命，需 agent 层增加内存监控和 fallback |
| Featuretools | pip install | **保留但定位为可选** | 维护模式 + NGS 单矩阵不匹配（6/10），Agent 根据数据形态决定是否调用 |

## 三、被否方案理由

### 3.1 CAAFE：从"拆出核心逻辑"降级为"纯设计参考"

**被哪条质疑驳倒**：集成评估师发现 CAAFE 的 `openai==0.28` 与 AIDE/mem0 的 `openai>=1.69` 存在致命依赖冲突（组合 5 评分 4/10）。同一 Python 环境无法共存两个 major 版本的 openai SDK。

**辩论中的共识**：代言人 1 在回应中完全承认此质疑，CAAFE 的定位从"拆出核心逻辑"调整为"纯设计参考"。红队 Issue #8（openai>=1.0 不兼容）和 Issue #5（变量名写反）进一步支持不复用代码的决策。

### 3.2 Notebook Intelligence：从"直接复用"降级为"纯设计参考"

**被哪条质疑驳倒**：红队 Q1 指出 GPL-3.0 的 "convey" 触发条件比调研报告理解的"对外分发"更宽泛，团队内部使用也可能构成 copyleft。集成评估师将 NBI 的推荐分降至 5/10。

**辩论中的共识**：代言人 2 在回应中承认法律风险，将 NBI 定位为"研读其设计模式后自研简化版"。PR #290/#323 的路径遍历漏洞进一步支持不复用代码。

### 3.3 Jupyter AI：从"参考 MCP 设计"保持不变，但强化"不复用代码"

**红队质疑的影响**：红队 Q1-Q3（v3 不稳定、端口硬编码、API 断裂）被代言人 3 全部承认。但这些质疑本身不挑战"参考设计"的定位，只是强化了"不要直接集成"的结论。

### 3.4 全自建：被集成评估师的数据驳倒

**被哪条质疑驳倒**：集成评估师给全自建评分 3/10，估算周期 11-16 周，远超 fork/集成方案的 7-8 周。AIDE 的 MLE-Bench 验证成果、mem0 的 56K stars 成熟度、MLflow 的行业标准地位均无法短期自研替代。

**红队论点被驳**：红队主张"全自建与 fork 工作量相当"，但集成评估师的数据证明全自建周期是 fork 方案的 2 倍。代言人在辩论中指出：全自建无法获得 MLE-Bench 验证，这是无法用钱买到的工程资产。

### 3.5 AutoML-Agent：法律硬性排除

CC BY-NC 4.0 禁止商业使用，无需辩论即排除。

## 四、Open Questions（给下游设计阶段）

### OQ1：mem0 的 metadata 丢失 bug 的长期方案

**现状**：insert-only 模式可规避 Issue #5160，但会增加存储膨胀。
**待决策**：
- 方案 A：定期清理旧记忆（自动过期策略）
- 方案 B：迁移至 MongoDB 后端（mem0 已修复此路径）
- 方案 C：在 mem0 之上自建 metadata 索引层，绕过 mem0 的 update 路径
**建议**：Phase 2 采用方案 A（insert-only + 定期清理），Phase 4 评估方案 C 的可行性。

### OQ2：AIDE 的模型路由修复方案

**现状**：Issue #78 证明 AIDE 的模型路由 regex 只覆盖 OpenAI/Anthropic/Gemini。
**待决策**：
- 方案 A：扩展 regex 匹配（0.5-1 人天）
- 方案 B：重写模型路由层为配置化映射表（1-2 人天，更灵活）
**建议**：Phase 1 采用方案 A（MVP 够用），Phase 3 评估方案 B。

### OQ3：OpenFE 的 NGS 高维数据内存问题

**现状**：Issue #62/#53 证明 OpenFE 的 O(n²) 内存复杂度对 10K+ 特征不可承受。
**待决策**：
- 方案 A：Agent 层限制特征子集规模（如先降维到 1K 再调用 OpenFE）
- 方案 B：用 LLM + Code Interpreter 重新实现 OpenFE 的 23 种算子（更灵活但成本更高）
- 方案 C：完全放弃 OpenFE，仅保留 Featuretools（但 Featuretools 也有 NGS 不匹配问题）
**建议**：Phase 1 跳过 OpenFE/Featuretools，Phase 3 评估方案 B（自研算子工具箱）。

### OQ4：MLflow 的本地部署简化

**现状**：Issue #23525 证明 MLflow 的本地部署不再"零配置"。
**待决策**：
- 方案 A：继续使用 MLflow 核心功能（log_params/log_metrics），接受其演进带来的维护成本
- 方案 B：自研极简实验追踪层（SQLite schema + 简单读写 API），2-3 人天
**建议**：Phase 1 采用方案 A，Phase 4 评估方案 B（若 MLflow 的维护成本超过阈值）。

### OQ5：NGS 领域知识注入的提示工程策略

**现状**：所有候选项目均为通用 ML 框架，无 NGS 特化。
**待决策**：
- 方案 A：在 Agent system prompt 中注入 NGS 领域知识（甲基化数据预处理、批次效应、CpG 位点选择等）
- 方案 B：自建 NGS 工具库（pysam/pyranges/biopython 封装）作为 Agent 可调用工具
- 方案 C：两者结合
**建议**：Phase 1 采用方案 A，Phase 2 开始方案 B 的工具封装。

## 五、改造成本总估算

### 5.1 按模块拆分

| 模块 | 来源 | 处理方式 | 工作量（人日） |
|------|------|---------|--------------|
| 探索引擎 | AIDE fork | Fork + 接入记忆层 + 修复路由 | 15-20 |
| 语义记忆 | mem0 | pip install + insert-only 适配 | 3-5 |
| 结构化追踪 | MLflow | pip install + 核心功能封装 | 1-2 |
| 特征工具 | OpenFE + Featuretools | pip install + Agent 工具封装 | 2-3 |
| 前端 UI | Streamlit | 自建 | 5-8 |
| ipynb 解析 | 自研 | 自建（参考 Jupyter AI/NBI） | 2-3 |
| Skill 系统 | Agent SDK 内置 | 直接使用 + NGS Skill 编写 | 3-5 |
| NGS 工具库 | pysam/pyranges/biopython | 自建封装 | 5-8 |
| 安全 hooks | 参考 OpenHands/SWE-agent | 自建 | 2-3 |
| **合计** | | | **38-57 人日（约 8-10 周）** |

### 5.2 关键假设

- 1 名高级 Python 工程师，熟悉 Anthropic SDK 和 sklearn/XGBoost
- AIDE fork 包含：树搜索核心保留，harness 替换为 Agent SDK，UI 层移除
- mem0 采用 insert-only 模式，不依赖 update 路径
- MLflow 仅使用核心追踪功能，不涉及 Model Registry/LLM 追踪
- OpenFE/Featuretools 为可选工具，不影响核心路径

### 5.3 风险预留

| 风险 | 预留 | 说明 |
|------|------|------|
| AIDE 路由修复复杂度超预期 | +3 人日 | 若 regex 扩展不足以覆盖所有本地模型场景 |
| mem0 metadata 丢失无法规避 | +5 人日 | 若 insert-only 模式导致不可接受的存储膨胀 |
| NGS 工具库封装复杂度 | +5 人日 | 若 pysam/pyranges 的 Agent 工具封装比预期复杂 |
| **总预留** | **+13 人日** | 建议按 10-12 周规划 |
